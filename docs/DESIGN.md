## 0. 一句話

讓 OpenWrt 的多台 AP 互相照應，替每支手機報路：插上同一個區網就自動找到彼此，記住每支手機在家裡每個位置「實際上哪台最好用」，再用 802.11k/v/r 告訴它往哪走。只報路、永遠不踢，手機不想換就退避。搭配任何有線或 mesh 回程使用，本身不負責回程連線。

**這不是 mesh 回程**：不處理 AP 之間怎麼連線、封包怎麼轉送（802.11s、batman-adv、EasyMesh 回程）。只做 mesh 系統裡「引導裝置連到對的 AP」那一半。

## 1. 目標與原則

**目標**：多台 AP 的家用網路裡，讓每支手機在家中每個位置，連到「經驗上最好用」的 AP 或頻段，而不只是訊號最強的那台。

**為什麼需要學習**：訊號最強不一定最好用，例如：
- 某台 AP 的回程比較慢；
- 某個位置剛好在兩台之間，換來換去；
- 某支手機在某台 AP 上就是比較不穩。

**原則（任何版本都不能違反）**

1. **永遠不踢**：
   - 不用門檻斷線，不送 Deauth／Disassoc；
   - 11v BTM 不設 Disassociation Imminent、不帶斷線計時。
   - OpenWrt 現有的 usteer、DAWN 都會用門檻踢人；本設計刻意不做。
2. **學習只能「調整」，不能「取代」安全規則**：固定規則（第 7.1 節）是底線；學習只能在限定範圍內放寬或收緊。最壞的情況，就是退回固定規則的行為。
3. **相對比較**：只有另一個選擇明顯比較好才建議。
4. **裝置說了算**：不支援 11k／11v 的裝置完全不碰；建議被拒絕或不理會就退避。
5. **看得懂、退得回**：每個建議都要能從紀錄看出「因為哪個位置、哪段經驗」；一個開關就能回到「只觀察」。
6. **能少就少**：不做主動探索（不為了學習故意把裝置推去別台試）；不做座標定位；Flash 寫入要有上限；第一版不做用不到的資料來源。
7. **不拖累 hostapd**：程式卡住或當掉，Wi-Fi 必須照常運作。因此**永遠不開 `notify_response`**（第 9.3 節）。

## 2. 名詞

| 名詞 | 意思 |
|---|---|
| BSS | 一個 AP 的一個頻段（一個 BSSID） |
| 樣本 | 某個時間點、某台裝置的一次 Beacon Report 整理結果 |
| 指紋 | 一個樣本整理成的向量：`{BSSID: dBm}`，加上「量了哪些頻道」 |
| 位置（群） | 同一台裝置、相似的指紋歸成一群，大致對應家裡某個地方（不知道名稱、不算座標） |
| 片段 | 裝置在同一個位置、連在同一個 BSS 的一段時間；結束時評一次分 |
| 經驗 | 每台裝置、每個位置、每個 BSS 累積的評分 |
| 模型 | 一台裝置的所有位置與經驗（第 8.3 節） |
| 服務 AP | 裝置目前連著的那台 AP，負責這台裝置的決定與模型 |

## 3. 整體架構

```
            ┌────────────── poloo-meshd（每台 AP 一個，ucode）──────────────┐
 hostapd ──▶│ 本機裝置表（get_clients 每 2 秒）                              │
 ubus 通知 ─▶│ beacon-report／bss-transition-response／assoc／disassoc       │
            │        │                                                      │
            │        ▼                                                      │
            │ 每台裝置的模型（只存「目前連在本機」的裝置）                    │
            │   位置分群 → 片段評分 → 經驗                                   │
            │        │                                                      │
            │        ▼                                                      │
            │ 決定層：固定規則 ＋ 學習調整 → 問 → 比 → 建議 → 看結果          │──▶ hostapd ubus
            │        ▲                                                      │   rrm_nr_set
            │        │ 鄰居 AP 表（20 秒有效）                                │   rrm_beacon_req
            │  收報告 ◀── 群播＋廣播 :27330（每 5 秒）──▶ 送報告               │   bss_transition_request
            │  模型交接 ◀── TCP :27330（裝置換 AP 時）──▶ 模型交接            │
            └──────────────────────────────────────────────────────────────┘
```

- **沒有協調者**。每台裝置的模型放在它的服務 AP 上，裝置換 AP 時模型跟著走（第 8.3 節）。
- 決定在服務 AP 做：它直接控制 11k／11v，也直接持有這台裝置的模型，不用等任何回覆。
- 任何一台 AP 不在，其他台照常運作；最壞情況是某些裝置的模型暫時拿不到，退回固定規則。

## 4. 資料來源與樣本

### 4.1 資料來源（v1 只用 A、C）

| 來源 | OpenWrt 取得方式 | 用途 | v1 |
|---|---|---|---|
| A. 服務 AP 量到的訊號 | `ubus call hostapd.<if> get_clients` 的 `signal` | 監看訊號變化、決定什麼時候問；片段評分輔助 | ✅ |
| B. 其他 AP 聽到的探測請求 | 訂閱 `hostapd.<if>` 的 probe 通知（**不開** `notify_response` 也收得到） | 裝置掃描時的跨 AP 訊號 | ❌ 延後 |
| C. 手機量到的（11k Beacon Report） | `rrm_beacon_req` 送請求，訂閱 `beacon-report` 通知 | **指紋的唯一來源** | ✅ |

**為什麼 v1 不做 B 和「AP 指紋 ↔ 手機指紋對照表」**：
- 不支援 11k 的裝置本來就不碰（原則 4），B 只能補兩次 Beacon Report 之間的空檔；
- 手機螢幕關著時很少掃描，探測請求的 MAC 又多半是隨機的；
- 對照表複雜度高、收益低。v1 先不做，實測證明有需要再加。

**AP 量的跟手機量的不一樣**：常差 10～20 dB（D3 實測：小米 10T 量到的一直比 AP 量到的強約 20 dB），而且不對稱。所以「哪台比較好」以手機量的為準，A 只用來判斷「訊號有沒有變」。

### 4.2 樣本格式

```json
{
  "sta": "7c:1e:52:00:00:a4",
  "t": 1795520000,
  "cur": "20:76:93:46:be:e4",
  "chans": [6, 36, 149],
  "v": { "20:76:93:46:be:e4": -61, "20:76:93:46:be:e2": -55, "aa:bb:cc:dd:ee:01": -70 }
}
```

- `chans`：**這次實際量了哪些頻道**（v1 新增，第 5.2 節用）。
- `v` 只放 SSID 相同的 BSS（主網路，`ssid_h` 相同）；訪客、IoT 網路不參與。
- 空的回報（BSSID 全 0、頻道 0、RCPI 0）：算「有回」，但不當樣本。

**RCPI 換算**：照標準是 `dBm = RCPI / 2 − 110`。
- D3 實測：有手機把有號數的 dBm 直接填在 RCPI 欄位（貼近 AP 時回 218，照標準是 −1 dBm，不可能）。
- 處理：照標準換算出 −10 dBm 以上（RCPI ≥ 200）**連續 2 次**，就記住這台「填的是有號數」，之後都照有號數換算（`rcpi > 127 ? rcpi − 256 : rcpi`）。這個旗標存在模型裡，跟著裝置走。

### 4.3 什麼時候取樣（同時也是固定規則的「問」）

| 時機 | 量哪些頻道 |
|---|---|
| 連上後 60 秒；之後每 10 分鐘；或 A 的訊號變化 ≥ 6 dB | **取樣集合**：所有在線鄰居 AP（同 SSID）＋本機另一個頻段的頻道，全部量 |
| 建議前的「問」（第 7.1 節），而且這個位置已經成熟 | 可以只量這個位置經驗前 3 名 BSS 的頻道（第 7.2 節） |

**不打擾的條件（任一成立就不問，延後到下一個時機）**：
- 裝置不支援 11k Beacon Report（看 `get_clients` 的 rrm 能力）；
- 最近 30 秒大多在省電狀態（不是單一瞬間）；
- **最近 10 秒的流量 > 1 Mbit/s**（手機量測時要離開目前頻道，有流量時會頓一下；通話、遊戲時不問）；
- 同一個介面已經有一個 Beacon Request 在等回覆（一次一個，逾時 6 秒）；
- 距離上次問這台不到 60 秒。

## 5. 位置分群

### 5.1 每台裝置各自分群

- 不同手機的天線、韌體不同，同一個位置的數字可能差 10～20 dB。混在一起分群會亂掉。
- 每台裝置各自分群，就不需要校正裝置之間的差異，也不需要全家一致的位置編號（這是第 8.3 節「模型跟著裝置走」的前提）。
- 代價：新裝置要累積一陣子才有位置（冷啟動，第 7.4 節）。

### 5.2 距離（v1 修正：只比兩邊都量過的頻道）

兩個指紋 `x`、`y`：

```
C = x.chans ∩ y.chans                         ← 兩個樣本都有量的頻道
K = { k ∈ x.v ∪ y.v : channel(k) ∈ C }       ← 只取在共同頻道上的 BSS
缺值補 FLOOR = −95 dBm                         ← 只有「量了這個頻道但沒聽到」才補
d(x, y) = Σ_{k∈K} w_k · |x_k − y_k| ／ Σ_{k∈K} w_k
w_k = 1 ＋ (max(x_k, y_k) − FLOOR) ／ 30       ← 越強的 BSS 權重越大
若 |K| < 2：距離無法判斷（回傳 null），這個樣本不參與分群
```

- **為什麼要改**：v0 把所有沒出現的 BSS 都補 −95。但建議前只量前 3 名頻道時，「沒量」會被當成「聽不到」，同一個位置會被算成很遠，產生大量假的新位置。
- 位置中心也要記錄每個 BSS 的「被量到次數」；中心裡某 BSS 沒有資料時，等同那個頻道沒量過。
- `channel(k)`：BSSID 對應的頻道，從鄰居表或樣本本身查。

### 5.3 線上分群

每台裝置最多 `K_MAX = 8` 個位置。每個位置存：中心向量（含每個 BSS 的量測次數）、樣本數、最後看到的時間、穩定度（最近樣本到中心的平均距離）。

```
新樣本 s：
  c* = 距離最近的位置；d* = d(s, c*.中心)（null 的位置跳過）
  若 d* ≤ JOIN_DB（6 dB）：
      對 s 有量到的每個 BSS：c*.中心[k] ← c*.中心[k] ＋ α·(s[k] − c*.中心[k])
      α = max(0.05, 1 / (c*.樣本數 ＋ 1))
      c*.樣本數 ＋＝ 1；c*.最後時間 ← now
  否則若 d* ≥ NEW_DB（10 dB）或沒有任何位置：
      開一個新位置（滿了就淘汰「樣本數 × 最近程度」最低的那個，連它的經驗一起刪）
  否則（6～10 dB 之間）：
      歸給 c*，但不更新中心（模糊地帶，不讓中心被拉走）
```

- **只有取樣集合（全部頻道）的樣本才能開新位置**；只量 3 個頻道的樣本只能歸入既有位置。
- **成熟條件**：樣本數 ≥ 5，而且跨過 ≥ 2 天，才拿來做決定。
- **合併**：兩個位置的中心距離 < `MERGE_DB`（4 dB）時合併（樣本數加權平均），經驗也合併。

### 5.4 判斷「現在在哪」

- 最近 2 分鐘內有樣本：用它判斷，信心 ＝ `1 − d*/NEW_DB`（下限 0）。
- 沒有：視為「不知道在哪」，**學習不參與**，只用固定規則。
- 信心 < 0.5：同上。

## 6. 經驗

### 6.1 片段

裝置在同一個位置、連在同一個 BSS 的一段時間。下列任一件事發生就結束：
- 換了 BSS（自己換、或照建議換）；
- 位置變了（連續 2 個樣本落在別的位置）；
- 斷線；
- 已經 30 分鐘（長片段切段評分，避免一段經驗分量太重）。

### 6.2 片段怎麼評分

指標（`iw dev <if> station get <mac>`、hostapd `get_clients`，依驅動而定）：

| 指標 | 來源 | 好 | 壞 |
|---|---|---|---|
| 掉線 | 斷線事件 ＋ **60 秒內又連回同 SSID（任何一台）** | 沒有 | 有 |
| 來回彈 | 換 BSS 的紀錄 | — | 換過來 2 分鐘內又換回去 |
| 重送比例 | `tx retries`／`tx packets` 的差值 | < 10% | > 30% |
| 預期傳輸量 | `expected throughput`（有提供的驅動才有） | 比這台裝置的中位數高 | 低很多 |
| 有沒有在用 | `tx/rx bytes` 的差值 | — | 太少就不評分（見下） |

**v1 修正**：
- **離開不算掉線**：斷線後 60 秒內沒有在任何一台 AP 出現（人出門、手機關 Wi-Fi），不扣分，片段照其他指標評分。否則靠近門口的 BSS 會被冤枉。
- **來回彈一定評分**：來回彈的片段通常很短、流量少，但它是最重要的負面經驗，不受「閒置不評分」排除。
- 閒置判定：片段內 `tx+rx bytes` < 200 KB 且沒有來回彈、沒有掉線 → 不評分。

```
q = 0.5
q ＋＝ 0.25（沒掉線、沒來回彈）
q −＝ 0.5（掉線）；q −＝ 0.3（來回彈）
q ＋＝ 0.15 × clamp((中位重送率 − 本段重送率) ／ 中位重送率, −1, 1)
q ＋＝ 0.10 × clamp(log2(本段預期傳輸量 ／ 中位), −1, 1)    （有這個欄位時）
q = clamp(q, 0, 1)
```

「中位」是這台裝置最近 50 個片段的中位數（存在模型裡）。

累積成好／壞計數（Beta 分布）：

```
經驗[位置][BSS] = { g, b, t_last }
g ＋＝ q；b ＋＝ (1 − q)
平均 = (g ＋ 1) ／ (g ＋ b ＋ 2)       ← 沒有經驗時是 0.5
把握 = g ＋ b                          ← 累積了多少（已經衰減過）
```

**預期**：大部分正常片段的 q 落在 0.75 附近，兩個 BSS 的平均要差到 0.2，幾乎只會來自掉線或來回彈。所以學習實際上最主要的效果是「避開這個位置常掉線、常來回彈的 BSS」。這是預期內的，不是 bug。

### 6.3 時間衰減

- 半衰期 `HALF_LIFE = 7 天`。
- 讀寫前先衰減：`g, b ×＝ 0.5^((now − t_last) ／ HALF_LIFE)`，然後 `t_last ← now`。
- 位置的樣本數用同樣方式衰減；衰減到 < 0.5，而且 30 天沒出現的位置就刪掉。

### 6.4 搬動偵測（階段 4 才做）

**AP 被搬了**（影響所有裝置）：
- 每台 AP 把自己模型裡的「位置中心偏差摘要」放進報告（第 8.2 節的 `drift` 欄位，選做），或由使用者手動觸發。
- 判定：對 BSS `X`，最近 24 小時的樣本在已成熟的位置上，`X` 的偏差（樣本 − 中心）——**≥ 3 台不同裝置**、在 **≥ 2 個不同位置**，平均 |Δ| ≥ 8 dB、方向一致；同時其他 BSS 的偏差平均 < 3 dB。
- 動作：跟 `X` 有關的經驗 `g, b ×＝ 0.1`；位置中心裡 `X` 的值改成「下次樣本直接覆蓋」；寫紀錄「X 好像被移動了，重新學習」。
- 因為模型分散在各台 AP，這個判定由**每台 AP 對自己持有的裝置**做；需要 ≥ 3 台裝置時，用報告裡的 `drift` 摘要彙整。細節在階段 4 再定。
- **新加入或拔掉的 AP**：從位置中心移除不存在超過 7 天的 BSS；新的 BSS 在下一次樣本時加進中心，不重置其他資料。

**裝置的使用習慣變了**（只影響這台裝置）：最近 3 天，這台的樣本有 > 50% 落在「新開的位置」或「模糊地帶」→ 這台的半衰期改成 1 天，直到比例降到 < 20%。

## 7. 跟固定規則怎麼合作

### 7.1 固定規則（底線，照搬 padavan-tw `ROAM-COOP` 第 6 節）

1. **問**：第 4.3 節的時機與不打擾條件。
2. **比**：
   - 跨 AP：候選比目前強 ≥ 10 dB，候選本身 ≥ −72 dBm，連續兩次。
   - 頻段引導：2.4G → 5G 要 5G ≥ −65 dBm；5G → 2.4G 要 5G ≤ −75 dBm、且 2.4G 強 ≥ 15 dB。都要連續兩次。
3. **建議**：送 BTM，附候選清單，`disassociation_imminent: false`，`abridged: true`，`validity_period: 30`。
4. **看結果**：
   - 收 `bss-transition-response`：狀態 0 = 接受；非 0 = 拒絕（例如 7 = 候選不夠好）→ 立刻退避。
   - 15 秒內在目標出現算成功（目標是別台 AP 時，看那台的報告 `sta` 有沒有它）。
   - 沒有就退避 10 分鐘 → 1 小時 → 24 小時。
5. **上限**：每台裝置每天 6 次；每台 AP 每小時 12 次，超過就自動退回觀察並記紀錄。

### 7.2 學習能調整的地方（有上下限）

前提：「現在在哪」的信心 ≥ 0.5，而且那個位置已成熟。

| 調整 | 條件 | 範圍 |
|---|---|---|
| **放寬**跨 AP 門檻 | 候選的「平均 − 目前 BSS 的平均」≥ 0.2，且候選的把握 ≥ 3 | 10 dB 最多降到 **5 dB**；候選本身仍要 ≥ −72 dBm |
| **收緊**（擋掉訊號強、經驗差的候選） | 候選的平均 ≤ 0.35，且把握 ≥ 3 | 這個位置不建議它；**不會**因此建議裝置離開目前的 BSS |
| BTM 候選順序 | 有經驗的候選 | 偏好值 `pref = 64 ＋ 191 × 平均`（1～255）；寫進 Neighbor Report 的 BSS Transition Candidate Preference 子元素 |
| 先問哪幾個頻道 | 這個位置經驗前 3 名的 BSS | Beacon Request 只量這些頻道（第 4.3 節） |
| 回 5G | 這個位置 5G 的平均 ≥ 0.6 | 「暫時掉到 2.4G 後建議回 5G」的門檻 −67 dBm 最多放寬到 −72 dBm |

**連續兩次、退避、每日上限、永遠不踢，學習都不能改。**

### 7.3 決定流程（虛擬碼）

```
on_beacon_report(sta, report):
    sample  ← fingerprint(report)                 # 第 4.2 節，含 chans
    if sample is empty: mark_responded(sta); return
    model   ← models[sta]                          # 本機持有（第 8.3 節）
    place, conf ← locate(model, sample)            # 第 5.4 節
    model.add_sample(sample)                       # 第 5.3 節
    cands   ← same_ssid_bss_in(report)
    for c in cands:
        margin_needed ← 10 dB
        if conf ≥ 0.5 and place.mature:
            e_cur ← exp(model, place, cur_bss); e_c ← exp(model, place, c)
            if e_c.mean ≤ 0.35 and e_c.n ≥ 3:  skip c                       # 收緊
            if e_c.mean − e_cur.mean ≥ 0.2 and e_c.n ≥ 3:
                margin_needed ← max(5, 10 − 25 × (e_c.mean − e_cur.mean))   # 放寬
        if rssi(c) − rssi(cur) ≥ margin_needed and rssi(c) ≥ −72:
            mark_confirm(sta, c)                   # 連續兩次才算
    best ← 已連續兩次成立的候選中，(經驗平均, 訊號) 最好的
    if best and rate_limits_ok(sta) and mode ≠ observe:    # shadow 只用固定規則的結果
        btm_request(sta, ordered_by_pref(cands), disassoc_imminent = false)
        log("建議", sta, place.id, best, margins, experience_used)
```

`shadow` 模式下，固定規則照常送；學習調整的部分只計算、只記錄「如果採用學習會怎麼做」。

### 7.4 冷啟動

- 新裝置、新位置都沒有成熟前，學習完全不參與，就是固定規則。
- 固定規則跑出來的片段一樣會評分、累積經驗，所以**不需要主動探索**。
- **已知的代價**：裝置在同一個位置大多只連同一個 BSS，其他 BSS 的經驗很難累積到把握 ≥ 3，「放寬」很少有機會觸發。自然的探索來源只有：裝置自己換 AP、固定規則的建議、AP 重開機。shadow 模式要量這件事（第 10 節的「雙經驗位置數」）。

## 8. 多台 AP 之間：報告與模型交接

### 8.1 傳輸層

| 項目 | 值 | 理由 |
|---|---|---|
| 報告協定 | UDP | 無連線；掉一個封包，5 秒後就有下一份 |
| 報告目的位址 | **群播 `239.255.77.77` ＋ 區網廣播 `255.255.255.255`，兩個都送** | 群播在交換器開了 IGMP snooping 卻沒有查詢者、Mesh／無線回程、群播轉單播時會默默消失；廣播是保底。收的一方用 `(node, seq)` 去重 |
| 埠 | `27330`（UDP 收送；TCP 用於模型交接） | 跟 padavan-tw TWR2 同一個埠 |
| TTL | 1 | 只在同一個區網 |
| 介面 | 只綁 LAN 橋接介面（`br-lan`，UCI 可改） | 不從 WAN 送出或收進 |
| 自己的封包 | `IP_MULTICAST_LOOP=0`；節點 MAC 跟自己一樣的丟掉 | 不把自己當鄰居 |
| 封包大小 | 每份報告一個封包，≤ 1400 位元組 | 不分片 |
| 開機時 LAN 還沒有位址 | 每秒重試，其他工作照常 | 不因開機順序卡住 |

> 實作前確認：ucode 的 socket 模組（`ucode-mod-socket`）在目標 OpenWrt 版本有沒有，能不能 `setsockopt(IP_ADD_MEMBERSHIP)`。不能的話，v1 先只用廣播。

### 8.2 報告格式（JSON，`v: 1`）

```json
{
  "v": 1, "seq": 1287, "node": "20:76:93:46:be:e3", "ip": "192.168.1.1", "name": "客廳",
  "bss": [
    { "band": 5, "bssid": "20:76:93:46:be:e4", "ch": 149, "bw": 80, "op": 128,
      "ssid_h": "9f1c2a7b", "cap": "kvr", "mdid": "a1b2", "ft": "local", "n": 2,
      "nr": "<hostapd rrm_nr_get_own 的 Neighbor Report 元素 hex>" }
  ],
  "sta": [ ["7c:1e:52:00:00:a4", 5, -58] ],
  "gone": [ ["3c:22:fb:00:00:10", 5, -79, 12] ]
}
```

| 欄位 | 意思 |
|---|---|
| `seq` | 每份報告遞增；去重、偵測掉封包 |
| `node` | LAN 橋接介面的 MAC，當作這台 AP 的身分 |
| `bss[].op` | 全球 op class（第 9.3 節對照） |
| `bss[].ssid_h` | SSID 的 CRC32，不送明文 SSID；只有相同的才是候選 |
| `bss[].cap` | `k`＝11k、`v`＝11v、`r`＝11r |
| `bss[].mdid`、`ft` | 11r 的 Mobility Domain 與金鑰做法（`local`＝`ft_psk_generate_local`、`r0kh`＝R0KH／R1KH、`iapp`＝padavan ralinkiappd） |
| `bss[].n` | 該 BSS 的裝置數；**v1 只記錄，不參與決策** |
| `bss[].nr` | `rrm_nr_get_own` 的值；**快取上一次成功的值**（`rrm_nr_get_own` 偶爾回 `Not found`） |
| `sta` | 目前連著的裝置：`[MAC, 頻段, AP 量到的 dBm]` |
| `gone` | 30 秒內離開的裝置：`[MAC, 頻段, 離開前 dBm, 幾秒前]` |

**截斷規則**：超過 1400 位元組時，先截 `gone`，再截 `sta`（依訊號由強到弱保留）；`bss` 一定送得出去。
**版本相容**：看不懂的欄位一律略過；新增欄位只加不改。

**11r 位元（v1 修正）**：設 11k 鄰居清單或 BTM 候選時，只有「目前 BSS 與候選的 `mdid` 相同、`ft` 相同，而且都有 `r`」才設 Neighbor Report 的 Mobility Domain 位元。padavan-tw 和 OpenWrt 之間 FT 不通，混用時設了這個位元，手機會去做快速漫遊、失敗後才退回完整認證，有些手機會卡住。

### 8.3 模型跟著裝置走（取代 v0 的協調者）

**誰持有**：每台裝置的模型，放在它目前的服務 AP 上。模型包含：位置（≤ 8）、經驗、中位數統計、RCPI 旗標、退避狀態、`ver`（最後更新時間）、`owner`（最後持有的節點）。

**裝置換到本機時**：
1. 本機沒有這台的模型（或本機的 `ver` 比較舊）：
   - 從鄰居報告的 `gone`（或還沒更新的 `sta`）知道它從哪台來 → 直接 TCP 連那台要模型；
   - 找不到來源（例如對方重開機過）→ 送一份 UDP 詢問 `{"t":"who","sta":...}`，有這台模型的 AP 回 `{"t":"have","sta":...,"ver":...}`，向 `ver` 最新的那台要。
2. 要不到（2 秒逾時）：用本機舊的模型；沒有就新建（冷啟動）。
3. 交接期間照固定規則運作，不等待。

**TCP 交接格式**：連上 `:27330`，送一行 JSON `{"t":"get","sta":"..."}\n`，對方回一行 JSON 模型（gzip 後 base64，或直接 JSON；單台約 2～4 KB）後關閉。

**衝突**：`ver` 新的勝出。裝置在兩台之間來回彈時，兩邊都可能更新；以最後更新時間為準，差 1 秒以內以 `node` 較大的為準。

**持久化**：每台 AP 把「最近 30 天服務過的裝置」的模型存 `/etc/poloo-mesh/models.json.gz`，每 6 小時寫一次、正常關機寫一次，**每天最多 4 次**。重開機後先讀回。

**為什麼不用協調者**：
- 第 5.1 節已經決定每台裝置各自分群，所以不需要全家一致的位置編號；v0 第 8.4 節擔心的「位置對不起來」不存在。
- 拿掉選協調者、模型快照、`obs`／`seg`／`ack`、500 筆佇列，決定時也不用多等一趟 `loc` 回覆。
- 壞掉的範圍只有「某幾台裝置的模型暫時拿不到」，退回固定規則。

### 8.4 收到報告怎麼處理

1. 解析失敗、`v` 不認得、`node` 是自己 → 丟掉。`(node, seq)` 看過 → 丟掉（群播與廣播重複）。
2. 找這台鄰居：已經認識就更新；不認識就占用空位或 300 秒沒報告的位置，記事件「找到另一台 AP」。表滿（8 台）就丟掉。
3. `bss`、`sta` 整批換掉（不是累加）；`gone` 同一台裝置不重複記。
4. `bss` 的 BSSID 或頻道變了 → 記事件；需要時更新 11k 鄰居清單。
5. 鄰居清單只有內容（BSSID、頻道、筆數、nr）變了才呼叫 `rrm_nr_set`。

### 8.5 時效與容量

| 項目 | 值 |
|---|---|
| 讀 hostapd、跑決定層 | 每 2 秒 |
| 送報告 | 每 5 秒；頻道變了立刻多送一份 |
| 鄰居離線 | 20 秒沒報告 |
| 鄰居位置回收 | 300 秒 |
| 裝置離開判定 | 連續 2 次讀不到（約 4 秒） |
| `gone` 保留 | 30 秒 |
| 斷線（不是漫遊） | 離開 20 秒後本機與所有在線鄰居都沒有它 |
| 鄰居 AP | 8 台 |
| 每台鄰居的 `sta` | 96 台 |
| 本機持有的模型 | 200 台（30 天沒出現的刪掉） |

### 9.1 套件結構

| 項目 | 名稱 |
|---|---|
| 套件 | `poloo-mesh` |
| LuCI（選做） | `luci-app-poloo-mesh` |
| 常駐程式 | `/usr/share/poloo-mesh/poloo-meshd.uc`，procd 管理（`/etc/init.d/poloo-mesh`，respawn） |
| 設定 | `/etc/config/poloo-mesh`（UCI） |
| ubus 物件 | `poloo-mesh`（`status`、`clients`、`neighbors`、`events`、`model <mac>`、`set_mode`） |
| 狀態 | `/tmp/poloo-mesh/status.json`、`/tmp/poloo-mesh/events`（最近 200 筆） |
| 模型 | `/etc/poloo-mesh/models.json.gz` |
| 決定紀錄 | `/tmp/poloo-mesh/decisions.log`（循環，256 KB） |
| 語言 | **ucode**（OpenWrt 22.03 起內建；`ubus`、`uloop`、`fs` 模組；`socket` 模組要確認版本）。演算法都是小量的向量運算，不需要 C |

UCI 範例：

```
config poloo-mesh 'main'
    option mode 'observe'          # off / observe / shadow / assist
    option iface 'br-lan'
    option port '27330'
    option multicast '239.255.77.77'
    option broadcast '1'
    option persist_interval '21600'
    option debug '0'
```

### 9.2 無線設定（`/etc/config/wireless`，每個主網路的 wifi-iface）

```
option ieee80211k '1'              # 11k：鄰居報告、Beacon Report
option bss_transition '1'          # 11v BTM
option ieee80211r '1'              # 11r（選用）
option mobility_domain 'a1b2'      # 全家相同；可以跟 padavan-tw 一樣由 SSID 算
option ft_over_ds '0'
option ft_psk_generate_local '1'   # PSK：各 AP 自己算 PMK-R1，AP 之間不用交換金鑰
```

- 需要完整版 wpad（`wpad-mbedtls`／`wpad-openssl`）；`wpad-basic-*` 不支援 11k。
- 2.4G、5G **同 SSID、同密碼、同加密方式**；不然手機會把建議當成「換網路」而不理會。
- 訪客、IoT 網路不開 k／v／r（舊裝置相容性）。
- **不要和 usteer、DAWN 同時跑**，會互搶。安裝腳本偵測到時警告。
- `ft_psk_generate_local` 只適用 PSK。WPA3-SAE 或 802.1X 要另外設定 R0KH／R1KH 與金鑰，而且不能用預設值。

### 9.3 hostapd ubus 對照

| 動作 | ubus（以目標版本為準） |
|---|---|
| 連線中的裝置、訊號、能力 | `call hostapd.<if> get_clients`：`signal`；11k／11v 能力看 `rrm` 與 extended capabilities |
| 自己的鄰居元素 | `call hostapd.<if> rrm_nr_get_own`（偶爾 `Not found`，要快取） |
| 設鄰居清單 | `call hostapd.<if> rrm_nr_set '{"list":[[bssid, ssid, nr_hex], ...]}'` |
| 啟用 k／v（執行期） | `call hostapd.<if> bss_mgmt_enable '{"neighbor_report":true,"beacon_report":true,"bss_transition":true}'` |
| 請手機量 | `call hostapd.<if> rrm_beacon_req '{"addr":..., "mode":..., "op_class":..., "channel":..., "duration":..., "bssid":"ff:ff:ff:ff:ff:ff"}'` |
| 收量測結果 | `subscribe hostapd.<if>`，收 `beacon-report` 通知 |
| 送建議 | `call hostapd.<if> bss_transition_request '{"addr":..., "neighbors":[nr_hex,...], "abridged":true, "disassociation_imminent":false, "validity_period":30}'` |
| **收建議的回覆** | 同一個訂閱的 **`bss-transition-response`** 通知（含 `status_code`） |
| 連線、斷線事件 | 同一個訂閱的 `assoc`、`disassoc` 等通知 |
| 每台的重送、預期傳輸量 | `iw dev <if> station get <mac>` |

**絕對不要呼叫 `notify_response`**：開了之後，hostapd 每個探測、認證、關聯請求都會等訂閱者回覆（最多 100 ms），官方文件也警告訂閱者沒回時 hostapd 會停止回應探測請求。程式卡住，整台 AP 就會從手機的清單上消失。不開也收得到 probe／assoc 通知，只是 hostapd 不等回覆——這正是我們要的。

**op class（全球表）**：2.4G 1–13 ＝ 81；5G 36–48 ＝ 115、52–64 ＝ 118、100–144 ＝ 121、149–161 ＝ 124、165 ＝ 125。（80 MHz 以上的 op class 128／129 只用在 Neighbor Report 的寬頻資訊；Beacon Request 用上表的 20 MHz op class。）量另一個頻段的頻道時，op class 照那個頻道算。

**padavan-tw 踩過的坑**：
- **一次一個**：同一個介面同一時間只送一個 Beacon Request，等回報（最多 6 秒）或逾時再送下一個；BTM 也是。
- **Randomization Interval、Number of Repetitions 要是 0**：D3 的 5G 驅動原本隨機最多約 67 秒，手機從來不回；改成 0 之後同一秒就回。hostapd 的 `rrm_beacon_req` 要確認實際填的值。
- **duration、op class 一定要自己填**。
- **能力判斷**：某個頻段連續 3 次問了沒回，只停用那個頻段的 11k 請求，另一個頻段照常；24 小時後重試。

### 9.4 開工前要先確認的（階段 0）

```
ubus -v list 'hostapd.*'            # 方法與參數名稱：rrm_*、bss_transition_request、bss_mgmt_enable
ubus subscribe hostapd.phy1-ap0     # 另一個終端送 rrm_beacon_req／bss_transition_request，看通知欄位
ubus call hostapd.phy1-ap0 get_clients   # signal、rrm、extended capabilities 欄位
iw dev phy1-ap0 station dump        # tx retries、expected throughput 有沒有
opkg list-installed | grep ucode    # ucode-mod-socket、ucode-mod-ubus、ucode-mod-uloop
```

- 舊版 hostapd 沒有 `beacon-report` 或 `bss-transition-response` 通知；沒有的話，指紋或結果判斷就拿不到。
- mt76、ath10k、ath11k 對 11k／11v 的支援程度不同，要在實際硬體上確認。

## 10. 模式與上線順序

| 模式 | UCI `option mode` | 做什麼 |
|---|---|---|
| `off` | 關 | 不跑 |
| `observe` | 觀察 | 報告交換、鄰居清單（11k 鄰居報告是被動回應，不算打擾）、記錄連線事件；**不送 Beacon Request、不送 BTM** |
| `shadow` | 影子 | 照固定規則送 Beacon Request 和 BTM；學習**只計算、只記錄**「如果採用學習會怎麼做」 |
| `assist` | 輔助 | 學習照第 7.2 節的範圍調整 |

**建議的上線順序**：`shadow` 跑 2 週 → 看紀錄：學習「放寬」或「收緊」的案例，事後的片段分數是不是真的比較好 → 好的話再開 `assist`。

**要看的數字**

| 數字 | 用途 |
|---|---|
| 建議次數、接受率（BTM 狀態 0）、成功率（15 秒內到達） | 手機配不配合 |
| 來回彈的比例（2 分鐘內換回去） | 門檻是不是太鬆 |
| 換過去後的片段分數 vs 換之前 | 建議有沒有讓體驗變好 |
| 學習放寬／收緊的次數，以及事後的分數 | 學習到底有沒有幫助 |
| **雙經驗位置數**：有幾個成熟位置同時有 ≥ 2 個 BSS 把握 ≥ 3 | 太低代表「放寬」派不上用場（第 7.4 節） |
| 每台裝置的位置數、成熟比例 | 分群是否合理（每台 2～5 個比較正常；太多代表門檻太嚴） |
| 被跳過的 Beacon Request（流量、省電）與實際送出的次數 | 打擾手機的程度 |
| 模型交接成功率、延遲 | 第 8.3 節是否可靠 |

## 11. 隱私與安全

- **不出區網**：TTL 1、只綁 LAN 橋接介面；模型只存在 AP 上。
- **不存**：主機名稱、IP、流量內容；只有 MAC、訊號、時間、分數。
- **隨機 MAC**：
  - Android、iOS 對每個網路固定一組隨機 MAC，通常可以照常學；
  - 會定期輪換 MAC 的模式，每換一次就是一台新裝置，一直停在冷啟動，等同固定規則。
- **假報告**：區網裡任何裝置都能送假報告；最壞是讓 AP 把不存在的 BSSID 當候選、或誤判裝置換過去。因為永遠不踢、學習只能在限定範圍內調整，影響有限。另一個影響是灌爆建議上限，讓功能自動退回觀察。
- **簽章（階段 6）**：報告、模型交接加 HMAC-SHA256（取前 16 位元組），金鑰由主網路 SSID＋密碼衍生；**簽章範圍包含 `seq` 與時間戳**，收的一方拒收時間差 > 30 秒或 `seq` 倒退的封包，防止重放。
- **11r**：見第 9.2 節最後一點。

## 12. 參數總表（起始值）

| 參數 | 預設 | 說明 |
|---|---|---|
| `FLOOR` | −95 dBm | 量了但沒聽到時補的值 |
| `JOIN_DB` | 6 dB | 樣本歸入位置的距離 |
| `NEW_DB` | 10 dB | 開新位置的距離 |
| `MERGE_DB` | 4 dB | 兩個位置合併的距離 |
| `K_MAX` | 8 | 每台裝置的位置上限 |
| 最少共同 BSS | 2 | 距離可判斷的下限 |
| 成熟條件 | 5 個樣本、跨 2 天 | 位置可以參與決定 |
| 信心門檻 | 0.5 | 低於這個值學習不參與 |
| 片段最長 | 30 分鐘 | 長片段切段評分 |
| 來回彈 | 2 分鐘 | 換過去又換回來 |
| 掉線判定 | 60 秒內連回 | 超過算「離開」，不扣分 |
| 閒置片段 | < 200 KB | 不評分（來回彈、掉線例外） |
| `HALF_LIFE` | 7 天 | 經驗半衰期；習慣改變時 1 天 |
| 不問的流量門檻 | 1 Mbit/s（10 秒平均） | 第 4.3 節 |
| Beacon Request 逾時 | 6 秒 | 一次一個 |
| 跨 AP 門檻 | 10 dB（學習最多放寬到 5 dB） | 第 7.2 節 |
| 收緊門檻 | 平均 ≤ 0.35、把握 ≥ 3 | 第 7.2 節 |
| 建議上限 | 每台每天 6 次、每台 AP 每小時 12 次 | 不能由學習改變 |
| 報告間隔／離線判定 | 5 秒／20 秒 | AP 之間 |
| 模型交接逾時 | 2 秒 | 第 8.3 節 |
| 寫 Flash | 每 6 小時、每天最多 4 次 | 第 8.3 節 |

## 13. 實作順序

| 階段 | 內容 | 前提 | 完成條件 |
|---|---|---|---|
| 0 | 確認硬體與 hostapd（第 9.4 節），把結果寫進 `docs/HARDWARE.md` | 一台 AP＋一支手機 | 每個 ubus 方法與通知都實際呼叫過、欄位記錄下來 |
| 1 | 報告收送（群播＋廣播）、鄰居表、自動 11k 鄰居清單、`observe` 模式、狀態與事件、ubus 物件 | 兩台 AP | 兩台互相找到、手機要鄰居報告時拿到對方 |
| 2 | 固定規則（第 7.1 節）：Beacon Request、比較、BTM、看結果、退避、上限；`shadow` 的固定部分 | 階段 1 | 手機實際被建議換 AP 並成功，紀錄看得懂。**到這裡就已經有用** |
| 3 | 取樣、分群、片段評分、模型持久化、模型交接（第 8.3 節）；`shadow` 記錄學習的「如果」 | 階段 2 穩定 | 兩週資料、第 10 節的數字都有 |
| 4 | 搬動偵測、習慣改變偵測 | 有 2 週以上資料 | — |
| 5 | `assist` 模式 | `shadow` 的數字證明有幫助 | — |
| 6 | LuCI、HMAC、讀 padavan-tw TWR2 報告（混用環境） | 選做 | — |

**測試**
- **離線重播**：`observe`／`shadow` 模式把事件（樣本、連線、斷線、片段）寫成 JSON Lines；分群、評分、衰減、搬動偵測在電腦上用 `ucode` 直接跑同一份檔案。演算法模組要跟 ubus／socket 分開，才能在電腦上跑。
- **兩個實例互收**：在電腦上用環境變數假裝節點 MAC 與 BSSID，跑兩個 `poloo-meshd`，測報告與模型交接。
- **手機配合度**：iOS、各家 Android 對 11k／11v 的反應差很多（小米 10T 會回 11k、會回 BTM，但會拒絕差距不大的建議）。階段 0、2 各家手機都測過再往下做。
- **搬動偵測**：實際把一台 AP 換個房間放，看 24 小時內有沒有觸發、有沒有誤觸發。

## 14. 跟 padavan-tw 混用

- padavan-tw 送的是 TWR2 純文字格式（`docs/reference/padavan-twr2-protocol.md`），本專案送 JSON，**v1 互不相通**，各自是兩個獨立的群組。
- 階段 6 可選：`poloo-meshd` 也解析 TWR2，把 padavan AP 當成鄰居候選。TWR2 的 `R` 行沒有 `nr`，要自己由 BSSID、頻道、頻寬、op class 組 Neighbor Report 元素。
- 11r 跨廠牌不通：padavan 的 `ft` 視為 `iapp`，跟 OpenWrt 的 `local` 不同，就不設 Mobility Domain 位元（第 8.2 節）。

## 15. v0 → v1 的修改

| # | 修改 | 原因 |
|---|---|---|
| 1 | 拿掉 `notify_response`；B 類資料（探測請求）延後 | 開了會讓 hostapd 等程式回覆，程式卡住時 AP 不回應探測請求 |
| 2 | 樣本記錄 `chans`；距離只比兩邊都量過的頻道；只有全頻道樣本能開新位置 | v0 把「沒量」當「聽不到」補 −95，只量 3 個頻道時會產生假位置 |
| 3 | ubus 對照補上 `bss-transition-response` | 看結果與退避需要知道手機有沒有拒絕 |
| 4 | 協調者改成「模型跟著裝置走」 | 每台裝置各自分群，不需要全家一致的位置編號；省掉選舉、快照、ack、佇列與決策延遲 |
| 5 | 記錄「雙經驗位置數」；寫明學習主要效果是避開掉線、來回彈 | 不做探索時，替代 BSS 的經驗很難累積 |
| 6 | 「離開」不算掉線；來回彈一定評分 | 出門斷線會冤枉門口的 BSS；來回彈片段常被當閒置排除 |
| 7 | 第一版砍掉 AP 指紋與對照表；有流量時不送 Beacon Request | 不支援 11k 的裝置本來就不碰；量測會讓手機頓一下 |
| 8 | 確認 `ucode-mod-socket`；群播＋廣播一起送 | socket 模組依版本；群播常被交換器／Mesh 擋 |
| 9 | 報告加 `seq`、`op`、`mdid`、`ft`、`nr`；11r 位元只在 MDID 與 FT 做法相同時設 | 去重；OpenWrt 需要 Neighbor Report hex；跨廠牌 FT 不通 |
| 10 | RCPI 有號數判定改成連續 2 次 | 避免單次異常值誤判 |
| 11 | HMAC 簽章包含 `seq` 與時間戳 | 防止重放 |
| 12 | 名稱統一為 PolooMesh／`poloo-mesh` | 見 `DISCUSSION.md` 第 5 節 |
