# OpenWrt 訊號指紋漫遊：設計規格

> 版本：2026-11-25 草案
> 來源：
> - padavan-tw 的 KVR 構想（2026-11-18「虛擬空間＋經驗學習」）；
> - 已實作的「AP 互助漫遊」（`docs/ROAM-COOP.md`、`tw_roamd.c`）；
> - D3 實機測試的經驗。
>
> 狀態：**設計，還沒有實作，也沒有實測**。參數是起點，要用實際資料調整。hostapd ubus 的方法名稱與欄位依版本而定，實作前先用 `ubus -v list hostapd.*` 確認（第 9.4 節）。

---

## 1. 目標與原則

**目標**：多台 AP 的家用網路裡，讓每支手機在家中每個位置，連到「經驗上最好用」的 AP 或頻段，而不只是訊號最強的那台。

**為什麼需要學習**：訊號最強不一定最好用，例如：
- 某台 AP 的回程比較慢；
- 某個位置剛好在兩台之間，換來換去；
- 某支手機在某台 AP 上就是比較不穩。

這些只能從經驗看出來。

**原則（沿用 padavan-tw，任何版本都不能違反）**

1. **永遠不踢**：
   - 不用門檻斷線，不送 Deauth／Disassoc；
   - 11v BTM 不設 Disassociation Imminent、不帶斷線計時。
   - OpenWrt 現有的 usteer、DAWN 都會用門檻踢人；本設計刻意不做。
2. **學習只能「調整」，不能「取代」安全規則**：
   - 固定規則（第 7 節）是底線；學習只能在限定範圍內放寬或收緊。
   - 最壞的情況，就是退回固定規則的行為。
3. **相對比較**：只有另一個選擇明顯比較好才建議。
4. **裝置說了算**：
   - 不支援 11k／11v 的裝置完全不碰；
   - 建議被拒絕或不理會就退避。
5. **看得懂、退得回**：
   - 每個建議都要能從紀錄看出「因為哪個位置、哪段經驗」；
   - 一個開關就能回到「只觀察」。
6. **能少就少**：
   - 不做主動探索（不為了學習故意把裝置推去別台試試看）；
   - 不做座標定位；
   - Flash 寫入要有上限。

## 2. 名詞

| 名詞 | 意思 |
|---|---|
| BSS | 一個 AP 的一個頻段（一個 BSSID） |
| 樣本 | 某個時間點、某台裝置的一組訊號量測 |
| 指紋 | 一個樣本整理成的向量：`{BSSID: dBm}` |
| 位置（群） | 同一台裝置、相似的指紋歸成一群，大致對應家裡某個地方（不知道名稱、不算座標） |
| 片段 | 裝置在同一個位置、連在同一個 BSS 的一段時間；結束時評一次分 |
| 經驗 | 每台裝置、每個位置、每個 BSS 累積的評分 |
| 協調者 | 負責維護模型的那台 AP（第 8 節） |

## 3. 整體架構

```
 每台 AP（hostapd ＋ kvr 常駐程式）                     協調者（其中一台 AP）
 ┌──────────────────────────────┐                   ┌─────────────────────────┐
 │ hostapd ubus：                │   觀察（樣本）     │ 每台裝置的模型：          │
 │  get_clients（AP 量到的訊號）  │ ────────────────▶ │  位置分群（第 5 節）      │
 │  beacon-report（手機量到的）   │   片段結果         │  經驗評分（第 6 節）      │
 │  probe 通知（還沒連上的訊號）  │ ────────────────▶ │  時間衰減、搬動偵測       │
 │                              │                   │  （第 6.3、6.4 節）       │
 │ 固定規則 ＋ 學習建議 → 決定    │ ◀──────────────── │ 建議：這台裝置在這個位置   │
 │ rrm_beacon_req／BTM／鄰居清單  │   位置判斷與偏好    │  偏好哪幾個 BSS、多有把握  │
 └──────────────────────────────┘                   └─────────────────────────┘
          ▲  每 5 秒：區網群播報告（AP 互相發現、鄰居清單、裝置在哪）  ▲
          └────────────────────────────────────────────────────────┘
```

- **決定在裝置目前連著的那台 AP 做**：它直接控制 11k／11v。協調者只提供「位置判斷」與「偏好」。
- **協調者不在時**，各 AP 照固定規則運作，不受影響（第 8.3 節）。

## 4. 資料來源與樣本

### 4.1 三種訊號

| 來源 | OpenWrt 取得方式 | 涵蓋 | 注意 |
|---|---|---|---|
| A. 連線中的 AP 量到的 | `ubus call hostapd.<介面> get_clients` 的 `signal`；或 `iw dev <介面> station dump` | 只有目前連著的那台 | 每 2～5 秒讀一次 |
| B. 其他 AP 聽到的探測請求 | 訂閱 `hostapd.<介面>` 的探測請求通知（要先呼叫 `notify_response` 才會送） | 裝置掃描時附近每台 AP 都聽得到 | 手機螢幕關著時很少掃描；隨機 MAC 的探測要過濾（第 11 節） |
| C. 手機量到的（11k Beacon Report） | `rrm_beacon_req` 送請求，訂閱 `beacon-report` 通知收結果 | 手機聽得到的每個 BSS | **最準**，但要手機支援 11k，而且每次問有成本 |

**指紋主要用 C**：「哪台比較好」以手機的角度為準。AP 聽到的跟手機收到的常差 10～20 dB（D3 實測：小米 10T 量到的一直比 AP 量到的強約 20 dB），而且不對稱。A、B 用來補：手機不支援 11k、或兩次問之間位置變了。

### 4.2 樣本格式

```json
{
  "sta": "7c:1e:52:00:00:a4",
  "t": 1795520000,
  "src": "bcn",
  "cur": "20:76:93:46:be:e4",
  "v": { "20:76:93:46:be:e4": -61, "20:76:93:46:be:e2": -55, "aa:bb:cc:dd:ee:01": -70 }
}
```

- `src`：`bcn`（手機量的）、`ap`（AP 量的；連線中的那台＋聽到探測的其他台）。**兩種分開存，不混在同一個向量**：數字的基準不同。
- `v` 只放 SSID 相同的 BSS（主網路）；訪客、IoT 網路不參與。
- 訊號換算：Beacon Report 的 RCPI 照標準是 `dBm = RCPI / 2 − 110`。
  - **D3 實測：有手機把有號數的 dBm 直接填在 RCPI 欄位**：例如貼近 AP 時回 218，照標準換算是 −1 dBm，不可能。
  - 處理：照標準換算出 −10 dBm 以上（RCPI ≥ 200），就記住這台「填的是有號數」，之後都照有號數換算。

### 4.3 什麼時候取樣

| 時機 | 樣本 |
|---|---|
| 裝置連上後 60 秒，之後每 10 分鐘，或 AP 量到的訊號變化 ≥ 6 dB | 送一次 Beacon Request，收到回報就是一個 `bcn` 樣本 |
| 每 30 秒 | 連線中的 AP 量到的值，加上 30 秒內其他 AP 聽到的探測，組成一個 `ap` 樣本 |
| 建議前（第 7 節的「問」） | 同一個 Beacon Request 的結果，順便當樣本 |

**不為了學習額外打擾手機**：Beacon Request 的時機跟原本的漫遊流程共用。省電中的手機不問（第 9.3 節）。

## 5. 位置分群

### 5.1 為什麼「每台裝置各自分群」

- 不同手機的天線、韌體不同，同一個位置的數字可能差 10～20 dB。混在一起分群會亂掉。
- 每台裝置各自分群，就不需要校正裝置之間的差異。
- 代價：新裝置要累積一陣子才有位置（冷啟動，第 7.4 節）。

### 5.2 距離

兩個指紋 `x`、`y`（同一種來源）：

```
K = x 和 y 的 BSSID 聯集
缺值補 FLOOR = −95 dBm（聽不到就當很弱）
d(x, y) = Σ_{k∈K} w_k · |x_k − y_k| ／ Σ_{k∈K} w_k
w_k = 1 ＋ (max(x_k, y_k) − FLOOR) ／ 30    ← 越強的 BSS 權重越大（近的 AP 比較能代表位置）
```

- 單位是 dB，好解釋：「這兩個位置平均差 4 dB」。
- 缺值補 FLOOR，而不是忽略：「這裡聽不到 X」本身就是位置資訊。

### 5.3 線上分群（不需要一次拿全部資料）

每台裝置最多 `K_MAX = 8` 個位置。每個位置存：
- 中心向量；
- 樣本數；
- 最後看到的時間；
- 「穩定度」：最近樣本到中心的平均距離。

```
新樣本 s：
  c* = 距離最近的位置；d* = d(s, c*.中心)
  若 d* ≤ JOIN_DB（6 dB）：
      c*.中心 ← c*.中心 ＋ α·(s − c*.中心)      α = max(0.05, 1 / (c*.樣本數 ＋ 1))
      c*.樣本數 ＋＝ 1；c*.最後時間 ← now
  否則若 d* ≥ NEW_DB（10 dB）：
      開一個新位置（滿了就淘汰「權重 × 最近程度」最低的那個，連它的經驗一起刪）
  否則（6～10 dB 之間）：
      歸給 c*，但不更新中心（模糊地帶，不讓中心被拉走）
```

- **成熟條件**：樣本數 ≥ 5，而且跨過 ≥ 2 天，才拿來做決定。避免一次經過就變成一個「位置」。
- **合併**：兩個位置的中心距離 < 4 dB 時合併（樣本數加權平均），經驗也合併。
- `ap` 指紋用同一套演算法、另一組位置。兩組的對應關係，用「同一時間的兩種樣本落在哪兩個位置」累積一張對照表；手機不回 11k 時，就用 `ap` 位置經由對照表找到 `bcn` 位置。

### 5.4 判斷「現在在哪」

- 最近 2 分鐘內有 `bcn` 樣本：用它判斷，信心＝`1 − d*/NEW_DB`。
- 沒有：用最近的 `ap` 樣本加對照表，信心再打 7 折。
- 信心 < 0.5：視為「不知道在哪」，**學習不參與**，只用固定規則。

## 6. 經驗

### 6.1 片段

裝置在同一個位置、連在同一個 BSS 的一段時間。下列任一件事發生就結束：
- 換了 BSS（自己換、或照建議換）；
- 位置變了（連續 2 個樣本落在別的位置）；
- 斷線；
- 已經 30 分鐘（長時間的片段切段評分，避免一段經驗分量太重）。

### 6.2 片段怎麼評分

OpenWrt 拿得到的指標（`iw station dump`、hostapd `get_clients`，依驅動而定）：

| 指標 | 來源 | 好 | 壞 |
|---|---|---|---|
| 連線是否中斷 | 斷線事件 | 沒有 | 片段內斷線（不是我們建議造成的） |
| 有沒有來回彈 | 換 BSS 的紀錄 | — | 換過來 2 分鐘內又換回去 |
| 重送比例 | `tx retries`／`tx packets` 的差值 | < 10% | > 30% |
| 預期傳輸量 | `expected throughput`（mac80211 有提供的驅動才有） | 比這台裝置的中位數高 | 低很多 |
| 實際有沒有在用 | `tx/rx bytes` 的差值 | — | 太少就**不評分**（閒置的片段沒有參考價值） |

每段算一個 0～1 的分數：

```
q = 0.5
q ＋＝ 0.25（沒斷線、沒來回彈）
q −＝ 0.5（斷線）；q −＝ 0.3（來回彈）
q ＋＝ 0.15 × clamp((中位重送率 − 本段重送率) ／ 中位重送率, −1, 1)
q ＋＝ 0.10 × clamp(log2(本段預期傳輸量 ／ 中位), −1, 1)    （有這個欄位時）
q = clamp(q, 0, 1)
```

累積成「好／壞計數」（Beta 分布），而不是平均：

```
經驗[裝置][位置][BSS] = { g, b, t_last }
g ＋＝ q；b ＋＝ (1 − q)
平均 = (g ＋ 1) ／ (g ＋ b ＋ 2)       ← 沒有經驗時是 0.5
把握 = g ＋ b                          ← 累積了多少（已經衰減過）
```

### 6.3 時間衰減

- 半衰期 `HALF_LIFE = 7 天`。
- 讀寫前先衰減（不用定時全部跑一次）：`g, b ×＝ 0.5^((now − t_last) ／ HALF_LIFE)`，然後 `t_last ← now`。
- 位置的樣本數用同樣方式衰減；衰減到 < 0.5，而且 30 天沒出現的位置就刪掉。

### 6.4 搬動偵測：加速遺忘

**AP 被搬了**（影響所有裝置）：
- 對每個 BSS `X`，比對最近 24 小時的 `bcn` 樣本：在已成熟的位置上，`X` 的訊號跟該位置中心的差（樣本 − 中心）。
- **≥ 3 台不同裝置**、在 **≥ 2 個不同位置**，`X` 的偏差平均 |Δ| ≥ 8 dB、方向一致；同時其他 BSS 的偏差平均 < 3 dB。這樣就判定 `X` 被搬了（或換了天線、擺放方向）。
- 動作：
  - 所有經驗裡跟 `X` 有關的 `g, b ×＝ 0.1`；
  - 所有位置中心裡 `X` 的值改成「下次樣本直接覆蓋」；
  - 寫紀錄「X 好像被移動了，重新學習」。
- **新加入或拔掉的 AP**：從所有位置中心移除不存在超過 7 天的 BSS；新的 BSS 在下一次樣本時加進中心，不重置其他資料。

**裝置的使用習慣變了**（只影響這台裝置）：
- 最近 3 天，這台的樣本有 > 50% 落在「新開的位置」或「模糊地帶」→ 這台的半衰期改成 1 天，直到比例降到 < 20%。
- 典型原因：搬家具、換房間、新的工作桌。

## 7. 跟固定規則怎麼合作

### 7.1 固定規則（底線，照搬 padavan-tw `ROAM-COOP` 第 6 節）

1. **問**：裝置支援 11k、不在省電、連上超過 120 秒；訊號變 ≥ 6 dB 或距上次 10 分鐘；同一台最少隔 60 秒。
2. **比**：
   - 跨 AP：候選比目前強 ≥ 10 dB，候選本身 ≥ −72 dBm，連續兩次。
   - 頻段引導：2.4G → 5G 要 5G ≥ −65 dBm；5G → 2.4G 要 5G ≤ −75 dBm、且 2.4G 強 ≥ 15 dB。都要連續兩次。
3. **建議**：送 BTM，附候選清單，不設 Disassociation Imminent。
4. **看結果**：15 秒內在目標出現算成功；沒有就退避 10 分鐘 → 1 小時 → 24 小時。
5. **上限**：每台每天 6 次；每台 AP 每小時 12 次，超過就自動退回觀察。

### 7.2 學習能調整的地方（有上下限）

前提：「現在在哪」的信心 ≥ 0.5，而且那個位置已成熟。

| 調整 | 條件 | 範圍 |
|---|---|---|
| **放寬**跨 AP 門檻 | 這個位置上，候選的「平均 − 目前 BSS 的平均」≥ 0.2，且候選的把握 ≥ 3 | 10 dB 最多降到 **5 dB**；候選本身仍要 ≥ −72 dBm |
| **收緊**（擋掉訊號比較強、經驗卻比較差的候選） | 候選的平均 ≤ 0.35，且把握 ≥ 3 | 這個位置不建議它；**不會**因此建議裝置離開目前的 BSS |
| BTM 候選順序 | 有經驗的候選 | 偏好值 `pref = 64 ＋ 191 × 平均`（1～255，越大越想要） |
| 先問哪幾個頻道 | 這個位置經驗前 3 名的 BSS | Beacon Request 先量這些頻道，減少手機掃描時間 |
| 回 5G | 這個位置 5G 的平均 ≥ 0.6 | 「暫時掉到 2.4G 後建議回 5G」的訊號門檻 −67 dBm 最多放寬到 −72 dBm |

**連續兩次、退避、每日上限、永遠不踢，學習都不能改。**

### 7.3 決定流程（虛擬碼）

```
on_beacon_report(sta, report):
    sample  ← fingerprint(report)
    place, conf ← locate(sta, sample)             # 第 5.4 節
    model.add_sample(sta, sample)                 # 第 5.3 節（協調者那邊）
    cands   ← same_ssid_bss_in(report)
    for c in cands:
        margin_needed ← 10 dB
        if conf ≥ 0.5 and place.mature:
            e_cur ← exp(sta, place, cur_bss); e_c ← exp(sta, place, c)
            if e_c.mean ≤ 0.35 and e_c.n ≥ 3:  skip c                       # 收緊
            if e_c.mean − e_cur.mean ≥ 0.2 and e_c.n ≥ 3:
                margin_needed ← max(5, 10 − 25 × (e_c.mean − e_cur.mean))   # 放寬
        if rssi(c) − rssi(cur) ≥ margin_needed and rssi(c) ≥ −72:
            mark_confirm(sta, c)                  # 連續兩次才算
    best ← 已連續兩次成立的候選中，(經驗平均, 訊號) 最好的
    if best and rate_limits_ok(sta):
        btm_request(sta, ordered_by_pref(cands), disassoc_imminent = false)
        log("建議", sta, place.id, best, margins, experience_used)
```

### 7.4 冷啟動

- 新裝置、新位置都沒有成熟前，學習完全不參與，就是固定規則。
- 用固定規則跑出來的片段一樣會評分、累積經驗，所以**不需要主動探索**。

## 8. 多台 AP 之間：交換與協調者

### 8.1 互相發現（沿用 padavan-tw TWR2 的做法，換成 JSON）

- 每台 AP 每 5 秒在區網群播一份報告：`239.255.77.77:27330`，UDP，TTL 1，只從 LAN 橋接介面送。
- 20 秒沒收到就當它離線。
- 報告內容（< 1400 位元組，一個封包）：

```json
{
  "v": 1, "node": "20:76:93:46:be:e3", "ip": "192.168.1.1", "name": "客廳",
  "coord": false,
  "bss": [
    { "band": 5, "bssid": "20:76:93:46:be:e4", "ch": 149, "bw": 80, "ssid_h": "9f1c2a7b",
      "cap": "kvr", "n": 2, "nr": "<hostapd rrm_nr_get_own 的鄰居元素 hex>" }
  ],
  "sta": [ ["7c:1e:52:00:00:a4", 5, -58] ],
  "gone": [ ["3c:22:fb:00:00:10", 5, -79, 12] ]
}
```

- `ssid_h`：SSID 的 CRC32，不送明文 SSID。只有相同的才是候選。
- `nr`：各 AP 用 `rrm_nr_get_own` 取自己的鄰居元素放進報告；收到的一方把同 SSID 的那幾筆用 `rrm_nr_set` 設進自己的 hostapd，就是 11k 鄰居清單。這跟 OpenWrt 的 static-neighbor-reports 做的是同一件事，只是自動交換。
- `sta`／`gone`：目前連著的裝置、30 秒內離開的裝置。用來確認建議成功、偵測換 AP、區分斷線與漫遊（`規格-KVR-AP間區網溝通` 第 7.3～7.5 節）。

### 8.2 協調者

- **誰當**：在線的 AP 裡節點 MAC 最小的那台；也可以在 UCI 指定（`option coordinator '1'`）。換人時記一筆紀錄。
- **其他 AP 送給協調者**（單播 UDP，同一個埠）：
  - `{"t":"obs", ...樣本}`：第 4.2 節的樣本。
  - `{"t":"seg", "sta":..., "place":..., "bss":..., "q":0.82, "reason":"ok"}`：片段結果（`place` 由協調者回覆的位置編號）。
- **協調者回覆**：
  - 收到 `obs` 後，回 `{"t":"loc", "sta":..., "place":"p3", "conf":0.8, "pref":[["bssid",0.81,6.2],...]}`：位置、信心、這個位置各 BSS 的平均與把握。
  - 連線中的 AP 收到後快取 2 分鐘，決定時直接用（第 7.3 節）。
- **掉封包**：
  - `obs` 掉了只是少一個樣本；
  - `seg` 帶序號，協調者回 `{"t":"ack","seq":n}`，沒收到就重送 2 次；
  - `loc` 沒收到，就照固定規則做。

### 8.3 協調者換人或不在

- 協調者每 10 分鐘把模型快照（壓縮後的 JSON）單播給「下一順位」的 AP。換人時，新的協調者從最近的快照接著學。
- 沒有協調者時（只剩一台、或剛開機）：各 AP 照固定規則，片段結果先存在記憶體佇列（上限 500 筆），找到協調者再送。

### 8.4 為什麼不是每台各自學

- 經驗發生在「裝置連著的那台」，但決定要比較的是「別台的經驗」；位置的編號也要全家一致。
- 各自學，要嘛每台都要全部的資料，要嘛位置對不起來。
- 一台協調者最簡單，壞掉時也只是退回固定規則。

## 9. OpenWrt 實作

### 9.1 套件結構（建議）

| 項目 | 建議 |
|---|---|
| 語言 | **ucode**（OpenWrt 22.03 起內建；有 `ubus`、`uloop`、`socket`、`fs` 模組，JSON 原生支援）。演算法都是小量的向量運算，不需要 C |
| 套件名稱 | `kvr-fingerprint`（例） |
| 常駐程式 | `/usr/share/kvr/kvrd.uc`，procd 管理（`/etc/init.d/kvr`，respawn） |
| 設定 | `/etc/config/kvr`（UCI）：模式、門檻、半衰期、協調者、Flash 寫入間隔 |
| 狀態 | `/tmp/kvr/status.json`、`/tmp/kvr/events`（最近 200 筆）；`ubus call kvr status` |
| 模型 | 協調者存 `/etc/kvr/model.json.gz`（第 9.5 節） |
| 介面（選做） | LuCI：每台裝置的位置數、每個位置偏好的 AP、最近的建議與結果 |

### 9.2 無線設定（`/etc/config/wireless`，每個主網路的 wifi-iface）

```
option ieee80211k '1'          # 11k：鄰居報告、Beacon Report（hostapd rrm_neighbor_report／rrm_beacon_report）
option bss_transition '1'      # 11v BTM
option ieee80211r '1'          # 11r（選用）
option mobility_domain 'a1b2'  # 全家相同；可以跟 padavan-tw 一樣由 SSID 算
option ft_over_ds '0'
option ft_psk_generate_local '1'   # PSK 網路各 AP 自己算 PMK-R1，不需要 AP 之間交換 R0KH／R1KH 金鑰
```

- 2.4G、5G **同 SSID、同密碼、同加密方式**；不然手機會把建議當成「換網路」而不理會。
- 訪客、IoT 網路不開 k／v／r（舊裝置相容性）。這是 padavan-tw 的做法：舊裝置改連 `_IoT` 網路。

### 9.3 hostapd ubus 對照

| 動作 | ubus（以目標版本為準） |
|---|---|
| 連線中的裝置、訊號、能力 | `call hostapd.<if> get_clients`：`signal`；11k／11v 能力看回傳的 rrm 與 extended capabilities 欄位 |
| 自己的鄰居元素 | `call hostapd.<if> rrm_nr_get_own` |
| 設鄰居清單 | `call hostapd.<if> rrm_nr_set '{"list":[[bssid, ssid, nr_hex], ...]}'` |
| 請手機量 | `call hostapd.<if> rrm_beacon_req '{"addr":..., "op_class":..., "channel":..., "duration":..., "mode":..., "bssid":"ff:ff:ff:ff:ff:ff"}'` |
| 收量測結果 | `subscribe hostapd.<if>`，收 `beacon-report` 通知（含 BSSID、op class、channel、RCPI、RSNI） |
| 探測請求的訊號 | 訂閱後呼叫 `notify_response`，會收到 probe／auth／assoc 通知（含 signal） |
| 送建議 | `call hostapd.<if> bss_transition_request '{"addr":..., "neighbors":[nr_hex,...], "abridged":true, "disassociation_imminent":false, "validity_period":30}'` |
| 斷線、連線事件 | 同一個訂閱的 `disassoc`、`assoc` 通知；或 `hostapd_cli` 的事件 |
| 每台的重送、預期傳輸量 | `iw dev <if> station get <mac>`（`tx retries`、`tx failed`、`expected throughput`） |

**padavan-tw 踩過的坑，換到 hostapd 也要注意**
- **一次一個**：同一個介面同一時間只送一個 Beacon Request，等回報（最多 6 秒）或逾時再送下一個；BTM 也是一次一個。
- **Beacon Request 的 duration、op class 一定要自己填**：
  - op class 用全球表：2.4G＝81；5G 36–48＝115、52–64＝118、100–144＝121、149–161＝124、165＝125。
  - 量另一個頻段的頻道時，op class 也要照那個頻道算。
- **Randomization Interval、Number of Repetitions 用 0**：D3 的 5G 驅動原本隨機最多約 67 秒、重複 1 次，手機從來不回；改成 0 之後同一秒就回。hostapd 預設值要確認。
- **空的回報**：剛連上的手機可能回 BSSID 全 0、頻道 0、RCPI 0 的報告。算「有回」，但不當樣本。
- **省電中不等於螢幕關著**：手機螢幕亮著、閒置時也會進省電。「省電中不打擾」要看一段時間內大多在省電，不是單一瞬間。
- **能力判斷**：在某個頻段連續 3 次問了沒回，只停用那個頻段的 11k 請求，另一個頻段照常。

### 9.4 開工前要先確認的

```
ubus -v list 'hostapd.*'            # 有哪些方法、參數名稱
ubus subscribe hostapd.wlan0        # 另一個終端送 rrm_beacon_req，看 beacon-report 通知的欄位
iw dev wlan0 station dump           # 驅動有沒有 expected throughput、tx retries
```

- 舊版 hostapd 沒有 `beacon-report` 通知；沒有的話，第 4.1 節的 C 就拿不到，只能用 A＋B（精準度差很多）。
- mt76、ath10k、ath11k 對 11k／11v 的支援程度不同，要在實際硬體上確認。

### 9.5 Flash 與記憶體

| 項目 | 上限 |
|---|---|
| 裝置 | 200 台（30 天沒出現的刪掉） |
| 每台的位置 | 8 個 |
| 每個位置的經驗 | 最多 8 個 BSS |
| 模型大小 | 約 200 × 8 ×（中心 8 個數字＋經驗 8 筆）≈ 壓縮後 100～200 KB |
| 寫 Flash | 協調者每 6 小時寫一次、正常關機時寫一次；**每天最多 4 次** |
| 記憶體 | 模型全部在記憶體，約 1～2 MB |

## 10. 模式與上線順序

| 模式 | UCI `option mode` | 做什麼 |
|---|---|---|
| `off` | 關 | 不跑 |
| `observe` | 觀察 | 交換、取樣、分群、評分都做；**不送任何請求**（Beacon Request 也不送，所以只有 A、B 的資料） |
| `shadow` | 影子 | 照固定規則送請求和建議；學習**只計算、只記錄**「如果採用學習會怎麼做」 |
| `assist` | 輔助 | 學習照第 7.2 節的範圍調整 |

**建議的上線順序**：
1. `shadow` 跑 2 週，累積位置與經驗。
2. 看紀錄：學習「放寬」或「收緊」的案例，事後的片段分數是不是真的比較好。
3. 好的話再開 `assist`。

**要看的數字**

| 數字 | 用途 |
|---|---|
| 建議次數、成功率（15 秒內到達） | 手機配不配合 |
| 來回彈的比例（2 分鐘內換回去） | 門檻是不是太鬆 |
| 換過去後的片段分數 vs 換之前 | 建議有沒有讓體驗變好 |
| 學習放寬／收緊的次數，以及事後的分數 | 學習到底有沒有幫助（`shadow` 跟 `assist` 比） |
| 每台裝置的位置數、成熟比例 | 分群是否合理（每台 2～5 個比較正常；太多代表門檻太嚴） |
| 搬動偵測觸發次數 | 太常觸發代表門檻太敏感 |
| Beacon Request 次數 | 打擾手機的程度 |

## 11. 隱私與安全

- **不出區網**：TTL 1、只綁 LAN 橋接介面；模型只存在協調者。
- **不存**：主機名稱、IP、流量內容；只有 MAC、訊號、時間、分數。
- **隨機 MAC**：
  - Android、iOS 對每個網路固定一組隨機 MAC，通常可以照常學；
  - 會定期輪換 MAC 的模式（例如 iOS 的「輪換」），每換一次就是一台新裝置。這種裝置一直停在冷啟動，等同固定規則。
  - 探測請求的 MAC 多半是隨機的，跟連線用的 MAC 對不起來；B 類樣本只收「已經連線過的 MAC」。
- **假報告**：
  - 區網裡任何裝置都能送假報告或假樣本；最壞是讓學習做出錯的偏好。
  - 因為學習只能在第 7.2 節的範圍內調整，而且永遠不踢，影響有限。
  - 要擋的話：報告與單播訊息加 HMAC，金鑰由主網路密碼衍生（同一組 Wi-Fi 密碼的 AP 才互相信任）。
- **11r**：`ft_psk_generate_local` 只適用 PSK。WPA3-SAE 或 802.1X 要另外設定 R0KH／R1KH 與金鑰；那些金鑰不能用預設值。padavan-tw 的聯發科驅動就卡在預設金鑰，換到 OpenWrt 時不要重蹈覆轍。

## 13. 實作順序（建議）

| 階段 | 內容 | 前提 |
|---|---|---|
| 0 | 確認硬體與 hostapd：`beacon-report` 通知、BTM、`rrm_nr_*`、`expected throughput`（第 9.4 節） | 一台 AP＋一支手機 |
| 1 | AP 互相發現、自動鄰居清單（第 8.1 節）、固定規則（第 7.1 節）、紀錄。**這一階段就已經有用**，等於 padavan-tw 現在的 KVR | 兩台 AP |
| 2 | 取樣、分群、片段評分，以 `observe`／`shadow` 模式累積 | 階段 1 穩定 |
| 3 | 協調者、模型快照、Flash 寫入 | 階段 2 |
| 4 | 搬動偵測、習慣改變偵測 | 有 2 週以上的資料 |
| 5 | `assist` 模式（第 7.2 節的調整） | `shadow` 的數字證明有幫助 |
| 6 | LuCI 介面、HMAC | 選做 |

**測試建議**
- **離線重播**：
  - 把 `observe` 模式的事件（樣本、連線、斷線）存成檔案；
  - 分群、評分、衰減、搬動偵測都可以在電腦上用同一份檔案反覆跑；
  - 調參數不用每次都上機。
- **搬動偵測**：實際把一台 AP 換個房間放，看 24 小時內有沒有觸發、有沒有誤觸發。
- **手機配合度**：iOS、各家 Android 對 11k／11v 的反應差很多（D3 實測小米 10T 會回 11k、會回 BTM，但會拒絕差距不大的建議）。先做階段 0、1，各家手機都測過再往下做。
