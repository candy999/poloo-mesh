# padavan-tw KVR：AP 之間的區網溝通規格

> 版本：2026-11-25，對應 padavan-tw v2026.11.24（f8c88e2）
> 程式：`trunk/user/rc/src/tw_roamd.c`（交換與決定層）、`tw_roam_drv.c`／`tw_roam.h`（驅動介面）、`trunk/user/ralinkiappd/iappd.sh`（11r 金鑰交換）、`rc/src/ralink.c`（Mobility Domain）
> 設計來源：`docs/ROAM-COOP.md`
> 本文寫的是**目前程式實際的做法**。設計有、程式還沒做的放在第 11 節；可以再優化的提案放在第 12 節，都還沒實作。

---

## 1. 目標與原則

**目標**：同一個區網裡的 padavan-tw AP 自動找到彼此、交換資料。拿這些資料：
- 告訴裝置附近有哪些 AP（11k 鄰居報告）；
- 挑出漫遊候選，用建議（11v）幫裝置換到比較好的 AP 或頻段；
- 事後確認裝置真的換過去了。

**原則（任何版本都不能違反）**
1. **永遠不踢**：不用固定訊號門檻斷線，不送 Deauth／Disassoc；建議不帶 Disassociation Imminent、不帶斷線計時。唯一的例外見第 7.7 節。
2. **相對比較**：只有另一個選擇明顯比較好才建議。
3. **裝置說了算**：不支援 11k／11v 的裝置完全不碰；不理會建議的就退避。
4. **能少就少**：交換的資料、頻率、參數都用最少的。
5. **零設定**：不用配對、不用填對方位址、不用共用金鑰；插上同一個區網就會找到彼此。
6. **一鍵退回**：模式切回「觀察」，就完全不送任何請求給裝置。交換本身照常進行。

## 2. 架構

每台 AP 各跑一個常駐程式 `tw-roamd`，由 watchdog 依 nvram `tw_roam_enable` 啟停，改模式會重新啟動。

```
              ┌──────────────── tw-roamd（每台 AP 一個）────────────────┐
 驅動 MAC 表 ─▶│ 本機裝置表 g_local（每 2 秒）                            │
 驅動事件    ─▶│ 11k 回報／11v 回覆                                       │
              │        │                                                │
              │        ▼                                                │
              │ 決定層：問 → 比 → 建議 → 看結果                          │
              │        ▲                       │                        │
              │        │ 鄰居 AP 表 g_peer      │ 11k 鄰居清單、11v 建議  │──▶ 驅動
              │        │（20 秒有效）            ▼                        │
              │  收報告 ◀── 239.255.77.77:27330 ──▶ 送報告（每 5 秒）     │
              └─────────────────────────────────────────────────────────┘
                     ▲                                   │
                     └──── 區網（br0，TTL 1）其他 AP ◀────┘
```

三種資料來源（`ROAM-COOP` 第 2 節）：

| 來源 | 內容 | 用途 |
|---|---|---|
| A. AP 自己看（驅動 MAC 表） | 每台連線裝置的訊號、頻段、連線秒數、省電 | 裝置現在在哪、狀況如何 |
| B. **AP 互相交換**（本文主題） | 別台 AP 的頻段、BSSID、頻道、能力；連著誰、訊號多少；剛離開誰 | 找候選、確認換過去、跨 AP 的歷史 |
| C. 裝置自己量（11k Beacon Report） | 裝置收到各候選的訊號 | 主要的決策依據：「哪台比較好」以裝置的角度為準 |

## 3. 傳輸層

| 項目 | 值 | 理由 |
|---|---|---|
| 協定 | UDP | 無連線、不用握手；掉一個封包，5 秒後就有下一份 |
| 目的位址 | 群播 `239.255.77.77` | 管理範圍內的群播（239/8），零設定就能互相找到 |
| 埠 | `27330` | 收送同一個埠 |
| TTL | `1` | 不經過路由器，只在同一個區網 |
| 送出介面 | `IP_MULTICAST_IF` 設為 `lan_ipaddr`，並 `SO_BINDTODEVICE br0` | 不會從 WAN 送出或收進來 |
| 自己的封包 | `IP_MULTICAST_LOOP=0`；收到節點 MAC 跟自己一樣的也丟掉 | 不把自己當鄰居 |
| 加入群組 | `IP_ADD_MEMBERSHIP`（以 br0 的位址） | 交換器有開 IGMP snooping 時，群播才會送到這台 |
| 綁定 | `0.0.0.0:27330`，`SO_REUSEADDR` | 允許重新啟動時馬上綁回 |
| 開機時 br0 還沒有位址 | 建立 socket 失敗就每秒重試，其他工作（讀驅動、寫狀態）照常 | 不會因為開機順序卡住 |
| 封包大小 | 每份報告一個封包，最多 1400 位元組（不分片） | 小於乙太網路 MTU，經過 VLAN、PPPoE 橋接也不會分片 |
| 收 | `recv` 最多 1500 位元組，非阻塞；和驅動事件一起用 `poll` 等，最多 1 秒 | 一個執行緒處理全部，不需要鎖 |

**防火牆**：群播封包從 br0 進來，padavan 的 INPUT 預設允許區網，不用另外開。

## 4. 訊息格式（TWR2）

純文字、UTF-8、每行以 `\n` 結尾、欄位用一個空白分隔。第一行是表頭，其他行第一個字元是型別。

### 4.1 語法

```
報告   = 表頭 名稱行 *頻段行 *裝置行 *離開行
表頭   = "TWR2" SP 節點MAC SP IP SP 2.4G頻道 SP 5G頻道 LF
名稱行 = "N" SP 名稱 LF
頻段行 = "R" SP 頻段 SP BSSID SP 頻道 SP 頻寬 SP 裝置數 SP SSID雜湊 SP 能力 LF
裝置行 = "C" SP 裝置MAC SP 頻段 SP 訊號 LF
離開行 = "G" SP 裝置MAC SP 頻段 SP 訊號 SP 幾秒前 LF
```

### 4.2 欄位

| 行 | 欄位 | 格式 | 來源／意義 |
|---|---|---|---|
| 表頭 | 版本 | `TWR1`／`TWR2` | `TWR2` 比 `TWR1` 多了 `R` 行 |
| | 節點 MAC | `aa:bb:cc:dd:ee:ff` | br0 的 MAC，當作這台 AP 的身分 |
| | IP | 點分十進位 | nvram `lan_ipaddr`；只用來顯示 |
| | 2.4G／5G 頻道 | 整數，沒有就 0 | 驅動目前的頻道（`SIOCGIWFREQ`） |
| N | 名稱 | 字串，最多 32 位元組 | nvram `computer_name`，沒有就用機型名稱；只用來顯示與記錄 |
| R | 頻段 | `2`／`5` | 每個主網路頻段一行（IoT 網路不列） |
| | BSSID | MAC | 該頻段介面的 MAC |
| | 頻道 | 整數 | 0 表示該頻段沒開，收的一方不會拿它當候選 |
| | 頻寬 | `20`／`40`／`80`／`160`（MHz） | 由 nvram `HT_BW` 推算，2.4G 最多 40 |
| | 裝置數 | 整數 | 該頻段主網路的裝置數；**目前只記錄，不參與決策** |
| | SSID 雜湊 | 8 位十六進位 | SSID 的 CRC32（多項式 0xEDB88320）；**不送明文 SSID**。只有雜湊相同才是漫遊候選 |
| | 能力 | `kv`、`kvr`、`-` | `k`＝11k、`v`＝11v（同一個 nvram 開關 `HT_80211KV`），`r`＝11r（`HT_80211R`） |
| C | 裝置 MAC、頻段、訊號 | MAC、`2`／`5`、dBm（整數） | 目前連在這台的裝置；訊號是 AP 量到的平滑值（EMA，權重 1/4） |
| G | 裝置 MAC、頻段、訊號、幾秒前 | 同上＋秒數 | 最近 30 秒內離開這台的裝置，訊號是離開前的平滑值 |

### 4.3 範例

```
TWR2 20:76:93:46:be:e3 192.168.1.1 6 149
N 客廳-D3
R 2 20:76:93:46:be:e2 6 20 3 9f1c2a7b kvr
R 5 20:76:93:46:be:e4 149 80 2 9f1c2a7b kvr
C 7c:1e:52:00:00:a4 5 -58
C a4:83:e7:00:00:21 2 -66
G 3c:22:fb:00:00:10 5 -79 12
```

### 4.4 組封包的規則

1. 依序寫：表頭 → `N` → 所有 `R` → `C` → `G`。
2. 剩不到 40 位元組時停止加 `C`；剩不到 48 位元組時停止加 `G`。所以 `R` 一定送得出去，裝置太多時截掉的是後面的 `C`、`G`。
3. 一行約 26 位元組，扣掉表頭和 `R` 行，一份報告大約可以放 48 台裝置。

### 4.5 版本相容

- 收的時候用 `TWR%d` 解析版本，`TWR1`、`TWR2` 都接受。`TWR1` 沒有 `R` 行，所以它的頻段不會變成候選，但它的 `C`、`G` 行照樣用。
- 看不懂的行一律略過。以後新增的行型別（例如 `L` 負載），舊版收到不會出錯；新增欄位只能加在行尾。
- 表頭解析失敗、版本小於 1、節點 MAC 格式錯，整份丟掉。

## 5. 節奏與時效

| 常數 | 值 | 用途 |
|---|---|---|
| `TWR_POLL_SEC` | 2 秒 | 讀驅動 MAC 表、跑決定層 |
| `TWR_REPORT_SEC` | 5 秒 | 送報告；同時更新自己的頻段資料、需要時更新 11k 鄰居清單、寫狀態檔 |
| `TWR_PEER_EXPIRE` | 20 秒 | 鄰居 AP 超過 20 秒沒報告就當它不在了（連續掉 3 份還留著），不再當候選、不算在線 |
| 鄰居位置回收 | 300 秒 | 表滿時，超過 5 分鐘沒報告的鄰居位置可以給新的 AP 用 |
| `TWR_GONE_POLLS` | 2 次 | 連續 2 次讀不到（約 4 秒）才算離開，避免驅動短暫漏讀 |
| `TWR_ROAM_WINDOW` | 30 秒 | `G` 行保留多久；裝置在一台消失後 30 秒內出現在另一台，算「換 AP」 |
| 5G 歷史 | 24 小時 | 裝置連過同 SSID 的 5G（本機或別台的 `C` 行）；用在「回 5G」 |
| 斷線判定 | 20 秒 | 裝置離開後 20 秒，本機和所有鄰居都沒有它，才記成斷線（不是漫遊） |

**容量上限**（全部在記憶體，不寫 Flash）

| 項目 | 上限 |
|---|---|
| 鄰居 AP | 8 台 |
| 每台鄰居的裝置（`C`） | 96 台 |
| 每台鄰居的剛離開（`G`） | 32 筆（循環覆寫） |
| 本機裝置 | 128 台 |
| 本機剛離開 | 32 筆（循環覆寫） |
| 5G 歷史 | 128 台 |

## 6. 收到報告怎麼處理

1. 解析表頭；節點 MAC 是自己就丟掉。
2. 找這台鄰居：已經認識就更新；不認識就占用空位或超過 300 秒沒報告的位置，並記一筆事件「找到另一台 AP」。表滿就丟掉這份。
3. 更新 IP、頻道、`last_seen`；**`C`、`R` 每份報告整批換掉**（不是累加），所以裝置離開那台後，下一份報告就不在了。
4. `R` 行：最多 2 個頻段。跟上一份相比 BSSID 或頻道變了，就記一筆「某台的某頻段換到頻道 X」。
5. `C` 行：存起來；頻段是 5 的，順便記進 5G 歷史。
6. `G` 行：同一台裝置不重複記；記下離開的時間（現在減去幾秒前）。

## 7. 交換來的資料拿來做什麼

### 7.1 11k 鄰居清單（告訴裝置附近有誰）

- **候選怎麼來**（`cands_for`）：
  - 本機的另一個頻段，SSID 雜湊要相同；
  - 加上 20 秒內有報告的鄰居 AP、SSID 雜湊相同、頻道不是 0 的 `R` 行；
  - 最多 8 筆。
- **Mobility Domain 位元**：目前頻段和候選都有 `r`，候選的 BSSID Info 就設 11r 位元，裝置知道可以快速漫遊過去。
- **只有變了才更新**：對候選清單（BSSID、頻道、筆數）算一個檢查碼，跟上次相同就不呼叫驅動。避免每 5 秒重寫一次驅動表。
- 只在建議模式、而且驅動能設定鄰居清單的頻段做（D3 2.4G、CR6608 兩頻段由程式回答；D3 5G 由驅動用掃描表回答）。

### 7.2 漫遊候選與 11v 建議

- 決定層用同一份候選清單請裝置量（Beacon Request 只量候選的頻道），再用裝置量到的數字比較。
- 建議的目標 BSSID 用 `radio_by_bssid` 對回是本機還是哪台鄰居。
- 規則細節（強 10 dB、連續兩次、退避）見 `ROAM-COOP` 第 6 節。

### 7.3 確認裝置真的換過去（看結果）

建議後 15 秒內：
- 目標是本機另一個頻段：本機裝置表裡它的頻段變了；
- 目標是別台 AP：那台下一份報告的 `C` 行出現這台裝置，而且頻段對得上。

這是 D3 5G（MT7612）唯一的結果判斷方式（驅動不回 BTM Response），所以**交換是決定層能不能運作的前提**。

### 7.4 偵測「換 AP」

裝置第一次出現在本機時，查所有鄰居：
1. 這台鄰居 30 秒內的 `G` 行有它 → 記「換 AP：從某台（頻段、離開前訊號）到這台」。用過的 `G` 標記作廢，不會重複算。
2. 不然，鄰居的 `C` 行還有它（對方還沒發現它離開）→ 一樣算換 AP。

### 7.5 區分「斷線」與「漫遊」

裝置離開本機 20 秒後：本機沒有它、所有在線鄰居的 `C` 行也沒有，才記成斷線（訊號太弱或離線）。有鄰居的話，換到別台不會被誤記成斷線。

### 7.6 回 5G（跨 AP 的歷史）

暫時掉到 2.4G 的裝置，只要 24 小時內在**任何一台**同 SSID 的 5G 出現過（別台的 `C` 行也算），就確定它支援 5G，可以建議回去。

### 7.7 每日選頻前移走裝置（本機，跟交換無關，列出來避免誤會）

`tw-wifi-acs` 要重新啟動某個頻段前，寫 `/tmp/tw-roamd.evacuate`。tw-roamd 對那個頻段支援 11v 的裝置送 BTM，請它們先移到另一個頻段（60 秒內做完）。
- **這是唯一帶 Disassociation Imminent 的建議**：頻段本來就要重新啟動，裝置一定會斷線，提早告訴它只是讓它先走。
- 不支援 11v 的不送。

## 8. 11r 的 AP 間溝通（金鑰交換）

跟 tw-roamd 分開，是驅動和 `ralinkiappd` 的事。

| 項目 | 做法 |
|---|---|
| Mobility Domain ID | rc 寫進 dat 的 `FtMdId1`：用 SSID 算 djb2 雜湊（h=5381，h=h×33+字元），取兩個 5 位元查表成兩個字元。同名的兩個頻段、家裡每台 padavan-tw 自動相同；不再用驅動預設的 `RT`（附近別家聯發科 AP 也用 `RT`） |
| 金鑰交換 | `ralinkiappd`（IAPP）在 br0 收 TCP／UDP 3517，兩個頻段都聽（D3：`-wi rai0 -wi ra0`）；新 AP 向原 AP 要 PMK-R1 |
| 防火牆 | `iappd.sh` 在 INPUT 對 br0 開 3517（先 `-C` 檢查，不重複加） |
| 鄰居快取 | br0、無線介面的 ARP 可達時間設 10 秒，換 AP 後區網很快找到裝置的新位置 |
| IoT 網路 | dat 的 `FtSupport` 第二格固定 0，IoT 網路不宣告 11r |
| 已知風險 | AP 之間加密 PMK-R1 用的是驅動的預設金鑰（`FT_KDP_KEY_DEFAULT`），ralinkiappd 沒開 `FT_KDP_KEY_FROM_DAEMON`，不能改。區網裡的裝置理論上能跟 AP 要金鑰資料；要改得同時修補驅動與 ralinkiappd |
| 相容性 | 只在跑聯發科驅動的 padavan-tw 之間有效，跟 Deco、OpenWrt 不通 |

## 9. 成本

| 項目 | 估計 |
|---|---|
| 每台 AP 送出 | 每 5 秒最多 1400 位元組 ≈ **280 B/s（2.2 kbit/s）**；一般家裡十幾台裝置時一份約 500 位元組 |
| 每台 AP 收 | 鄰居數 × 上面；8 台鄰居最多約 2.2 KB/s |
| CPU | 每 5 秒解析幾百位元組的文字；每 2 秒讀一次驅動表。D3 上量不出負載 |
| 記憶體 | 靜態陣列；鄰居表最大約 8 ×（96 + 32）筆 |
| 空中時間 | 橋接器沒有過濾群播時，報告也會從 Wi-Fi 送出（群播用基本速率）。每 5 秒一個封包，在 2.4G 最低速率下約 0.2% 的空中時間（估計，沒實測） |
| Flash | 不寫；只有決定紀錄 `roam.log` 在 `/etc/storage`（記憶體），存設定時才進 Flash，最多 32 KB |

## 10. 安全與隱私

| 項目 | 現況 |
|---|---|
| 不出區網 | TTL 1、綁 br0、群播只在區網 |
| 不送的東西 | 密碼、金鑰、明文 SSID（只送 CRC32）、主機名稱、裝置 IP |
| 會送的東西 | 裝置 MAC、頻段、訊號、AP 的 BSSID 與頻道，以區網明文傳送 |
| 認證 | **沒有**：區網裡任何裝置都能送假報告 |
| 假報告最壞的影響 | 讓 AP 把不存在的 BSSID 當候選、或誤判裝置已經換過去；因為「永遠不踢」，最多是建議裝置去一個不存在的 AP（裝置會拒絕），不會讓裝置斷線。另有上限：每台裝置每天 6 次、每台 AP 每小時 12 次，超過自動退回觀察 |
| 防呆 | 表頭格式、MAC 格式、頻段只收 2／5、各表有上限、每份報告整批取代（不會被灌爆） |

## 11. 設計有、程式還沒做的

| 項目 | `ROAM-COOP` 的設計 | 目前程式 |
|---|---|---|
| 群播被擋時改用廣播 | 中間交換器或 Mesh 開了 IGMP snooping、但沒有查詢者時，改送區網廣播（同一個埠） | **沒有**，只送群播 |
| 截斷時依訊號排序 | 裝置多時，`C`／`G` 依訊號排序後截斷 | **沒有排序**，照裝置表順序，滿了就停 |
| 裝置數參與決策 | 第一版只記錄 | 只記錄（跟設計一致） |
| `C` 行區分主網路／IoT | 沒寫 | `C` 行包含 IoT 網路的裝置、沒有標記。用途（確認換過去、5G 歷史）目前不受影響，但別台看不出差別 |

## 12. 可以再優化的地方（提案，都還沒做）

依「穩定優先」，只有實測遇到問題才做：

1. **廣播退回**（補第 11 節第 1 項）：某台 AP 在 60 秒內一份別人的報告都沒收到、但 ARP 表裡有別的 padavan-tw，就改送 `255.255.255.255:27330`；收的一方兩種都接受（內容相同）。
2. **頻道變了立刻送**：現在換頻道最多 5 秒後才通知鄰居。在 `tw-wifi-acs` 換完頻道後、或 `R` 行內容變了，立刻多送一份，鄰居清單更快更新。
3. **報告簽章**：用主網路 SSID＋密碼衍生一把金鑰（例如 HMAC-SHA256 取前 8 位元組），加一行 `S <簽章>`；舊版會略過未知的行，所以相容。只有同一組 Wi-Fi 密碼的 AP 能互相信任，第 10 節的假報告就擋得掉。
4. **`C` 行依訊號排序，並標記 IoT 網路**（例如 `C <MAC> <頻段> <訊號> g`），補第 11 節第 2、4 項。
5. **不讓報告從 Wi-Fi 送出**：只有有線回程的 AP 時，可以用 ebtables 擋住 239.255.77.77 從無線介面出去，省下空中時間。但無線回程（中繼、Mesh）的 AP 需要它，所以要做成選項或自動判斷。
6. **負載參與決策**：`R` 行的裝置數已經在送，之後可以在兩個候選訊號差不多時，偏向裝置比較少的那台。
7. **CR6608、多台 AP 實測**：目前只在單台 D3 上驗證過交換的收送與決定層。多台 AP 之間的「換 AP」偵測、跨 AP 建議、11r FT 金鑰交換都還沒實機測過。

## 14. 移植到 OpenWrt

交換協定、時效、決策規則照搬。只有驅動那一層換成 hostapd 的 ubus（`ROAM-COOP` 第 9 節）：

| 動作 | padavan（聯發科私有驅動） | OpenWrt（hostapd） |
|---|---|---|
| AP 之間交換 | 本文的 TWR2 群播 | 同一套（ucode 或小 C 程式） |
| 讀裝置與訊號 | 驅動 MAC 表 ioctl | `ubus call hostapd.<介面> get_clients` |
| 設鄰居清單 | 私有 OID／掃描表 | `rrm_nr_set` |
| 送 Beacon Request | 私有 OID／`iwpriv BcnReq` | `rrm_beacon_req` |
| 送 BTM | 私有 OID | `bss_transition_request`（`disassociation_imminent: false`） |
| 11r 金鑰交換 | ralinkiappd（3517） | hostapd 內建的 R0KH／R1KH 設定 |
